# Task Board（轻量版）

## 触发条件

**自动激活**：用户下达**多步骤任务**（≥2个独立操作，如"先查客户再匹配房源"、"抓取房源并写入表格"、"修复问题并验证"）时**必须自动激活**，无需用户说特定关键词。

**显式激活**：用户说"任务看板"时也激活。

**不激活**：单一步骤的简单查询（如"今天天气"、"你是谁"）不需要激活。

## 激活时强制行为（红线）

1. **首次加载**：激活后**第一轮回复必须先调用 `task_board_state.py load`** 读取当前进度。
2. **严禁跳过**：不得在未 load 状态的情况下直接开始执行任务。
3. **无状态 → 立即规划**：如果 load 返回"无状态文件"，说明是新任务。**必须立即列出 1-N 步执行计划，开始执行第 1 步**。严禁调用 clear。严禁反复 load。
4. **有状态 → 续接**：如果 load 显示之前卡在某个步骤，必须从该步骤续接，**严禁重置回步骤 1**。
5. **里程碑保存**：每完成一个实质性步骤后，调用 `save` 更新状态。**不要每轮都 save**，只在步骤完成时保存。
6. **防死循环**：如果同一个工具调用连续返回相同结果且无实质进展，**立即停止，转向实际业务操作**。

## 📋 视觉化 TODO 列表（每轮展示）

**激活后，第一轮回复必须做的第一件事：列出完整的 1-N 步计划，一条都不能少。**

格式示例：
```
📋 执行计划：
1. 第一步：明确需求和数据范围
2. 第二步：XXX
3. 第三步：XXX
4. 第四步：XXX
5. 第五步：XXX
6. 第六步：验证并交付

🔄 当前执行：第 1 步
```

**铁律：**
- **必须完整列出**：第一步就要展示全部 123456，**严禁只说"步骤1/N"但不列出其他步骤**
- **完成即划掉**：后续每轮回复开头，用 `~~删除线~~` + `✅` 标记已完成项
- **当前项高亮**：正在执行的步骤用 `🔄 当前执行：第 N 步` 标注
- **先列计划再提问**：列出完整计划后，才可以开始提问或执行第一步

## 看板格式

```
[看板] 🎯目标 | 📍步骤3/7 | ✅2步 | ⚠️风险 | 🔄下一步
[看板] 🎯目标 | 📍当前状态 | ✅已完成 | ⚠️风险 | 🔄下一步
```

## 状态标记

| 标记 | 含义 |
|------|------|
| `[ ]` | 未开始 |
| `[~]` | 进行中 |
| `[x]` | 已完成（须附验证证据） |
| `blocked` | 阻塞 → 必须附下一步动作 |
| `waiting` | 等待用户回复 |

## 方案对比（≥2个候选时强制执行）

```
⚖️ 方案对比:
| 方案 | 优势 | 劣势 | 风险 | 成本 |
|------|------|------|------|------|
| A | ... | ... | ... | ... |
| B | ... | ... | ... | ... |
✅ 推荐: B
```

## 破坏性操作拦截

检测到以下操作，**立即停止**，输出确认提示：

**破坏性操作范围：**
- 删除文件/记录（Excel行删除）
- 覆盖已有配置/数据/文件
- 批量操作（≥2条记录）
- 外发消息（给客户发微信/短信/打电话）
- 修改客户等级/意向区域等关键字段

**确认提示格式：**
```
⚠️ 破坏性操作检测
操作：[具体描述]
风险：[具体风险说明]
→ 请回复"确认"继续，或告诉我需要调整什么
```

## 内联权限检查逻辑（无需subprocess）

### PermissionMode 三级

| 模式 | 允许操作 |
|------|----------|
| `ReadOnly` | 读取、查询、搜索 |
| `WorkspaceWrite` | 写入、编辑、更新、跟进 |
| `DangerFullAccess` | 删除、覆盖、批量、外发消息 |

### 判断规则（直接写在python工具调用里）

```python
DESTRUCTIVE_PATTERNS = [
    r"删除", r"移除", r"清空", r"erase", r"delete",
    r"覆盖", r"重写", r"overwrite",
    r"批量", r"全部.*修改",
    r"发.*客户", r"发送.*微信", r"发.*短信", r"打电话",
    r"修改.*等级", r"更改.*等级", r"调整.*等级"
]

def check_destructive(action):
    for p in DESTRUCTIVE_PATTERNS:
        if re.search(p, action, re.IGNORECASE):
            return True
    return False
```

## 执行循环

1. **加载状态**：**仅激活时调用一次 `task_board_state.py load`**。后续轮次不需要反复 load，除非需要确认之前卡在哪一步。
2. **PreTool 检查**：直接用上面的内联逻辑判断是否破坏性操作（不再调用 hooks_runner.py）
3. **三思而后行**：
   - 回滚方案：若这一步出错，退回到 [上一步状态]
   - 未考虑风险：[风险描述]，若发生我会 [处理方式]
   - 验证方式：完成标志是 [具体验证标准]
4. **执行 + 收集证据**
5. **输出反馈**：
   ```
   [反馈]
   - 执行结果：成功/失败
   - 产出：[具体产出]
   - 下一步建议：[建议]
   ```
6. **更新状态**：`python task_board_state.py save "目标" "步骤X/Y" "当前" "已完成" "风险" "下一步"`（**仅在步骤完成时调用**）
7. **推进下一步**：进入下一轮时，继续执行下一个步骤，不要重新 load。

**🚨 防死循环红线**：
- **严禁**在每轮回复中重置进度到"步骤1"。必须基于 `load` 的结果递增步骤。
- 若连续 2 次工具调用返回相同结果且无实质进展，**必须停止并报错**，等待用户指示。
- **严禁反复调用 `clear` 或 `load` 超过 2 次**。load 返回"无状态文件"后，立即进入执行。
- **任务进行中严禁将"演示看板格式"作为主要目标**，必须聚焦于实际业务产出。看板只是状态同步工具，不是表演舞台。

**关键优化**：不再通过 subprocess 调用 hooks_runner.py，权限判断和破坏性检测直接内联在 SKILL.md 中，由 agent 自行判断。

## 状态脚本

**执行路径**：脚本位于 `skills/task-board/scripts/task_board_state.py`，调用时必须指定完整路径：

```bash
# 保存状态
python skills/task-board/scripts/task_board_state.py save "目标" "步骤X/Y" "当前" "已完成" "风险" "下一步"

# 读取状态
python skills/task-board/scripts/task_board_state.py load

# 清除状态
python skills/task-board/scripts/task_board_state.py clear

# 检查状态
python skills/task-board/scripts/task_board_state.py status

# 手动压缩历史（超过6条或token使用率超60%时）
python skills/task-board/scripts/task_board_state.py compact

# 手动压缩并提供摘要
python skills/task-board/scripts/task_board_state.py compact "<summary>...</summary>"

# 显示压缩摘要
python skills/task-board/scripts/task_board_state.py summary

# 显示 token 使用量
python skills/task-board/scripts/task_board_state.py tokens
```

**自动压缩**：每次save时自动检查，触发条件（满足任一即可）：
- 历史超过6条
- token使用率超过60%（针对200K上下文窗口优化）

**摘要格式**（参照 claw-code summarize_messages）：
```xml
<summary>
任务看板历史压缩摘要:
- 压缩范围: X 条历史记录
- 已完成步骤: Y/X
- 最近操作: ...
- 待办事项: ...
- 关键文件: ...
- 当前工作: ...
</summary>
```

## 🚨 避坑指南 (Pitfalls)

1. **严禁占位符**：`task_board_state.py` 中的配置项（如 `MAX_CONTEXT_TOKENS`）绝不能使用 `***` 等占位符，必须是真实数值。否则在触发自动压缩或 Token 估算时会报 `SyntaxError` 导致脚本直接崩溃。
2. **技能可见性红线**：OpenClaw 加载技能强依赖 **YAML frontmatter**（文件头部必须有 `---\nname: xxx\ndescription: xxx\n---`）。缺少该头部的技能文件虽然在磁盘上存在，但 Gateway 扫描时会直接忽略，导致 Agent **完全无法感知**（表现为问它有哪些技能时，大量技能缺失）。
3. **状态管理铁律**：**仅激活时 load 一次**。load 返回"无状态文件"→ 立即规划并开始执行第 1 步。有状态→ 续接。后续轮次继续执行即可，不要反复 load/clear。
4. **🚨 被动触发设计根本失效（2026-05-03 发现）**：
   - **问题**：SKILL.md 原设计"唯一触发词：用户说'任务看板'"，导致 Agent 在执行多步骤任务时**根本不加载看板**，看板形同虚设。
   - **根因**：Agent 的 SOUL.md 里没有任何"多步骤任务必须检查进度"的硬性指令。技能只是被动加载的文档，没有系统级强制力。
   - **修复**：(1) SKILL.md 改为**自动激活**（多步骤任务自动触发，无需关键词）；(2) 在 SOUL.md 新增"多步骤任务强制约束"模块，将看板规则写入 Agent 的核心行为准则。
   - **教训**：任何需要 Agent **持续遵守**的约束，必须写在 SOUL.md/系统提示中，不能只放在被动触发的技能里。技能适合"工具使用指南"，SOUL.md 适合"行为纪律"。
5. **状态文件卡死检测**：如果 `.task_board_state.json` 中连续 ≥3 条历史记录内容完全相同（步骤、当前状态、下一步全部一样），说明 Agent 已进入死循环。**必须立即清除状态文件**，否则下次加载会继续卡住。

## 禁止行为

- ❌ 看板比执行还长
- ❌ 一次列十几个事项同时进行
- ❌ 没有证据就宣布找到根因
- ❌ [x] 完成但没有验证证据
- ❌ blocked 但没有具体原因和下一步动作
- ❌ 破坏性操作不输出确认就执行
- ❌ 有多个方案不对比直接选
